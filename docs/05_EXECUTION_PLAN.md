# 실행 계획

## 1. 의사결정 우선순위

1. 데모가 끝까지 재현되는가
2. 안전 논리가 명확한가
3. 세종의 실제 문제와 연결되는가
4. AI가 꼭 필요한 이유가 보이는가
5. 기술 구조가 실제 확장 경로를 갖는가
6. 화면이 흥미로운가

## 2. 역할

| 역할 | 책임 |
|---|---|
| 제품·발표 | 문제 정의, 고객 인터뷰, 발표 서사, 범위 통제 |
| 프론트엔드 | 관제 대시보드, 지도·교차로 상태, 승인 UI |
| 백엔드·데이터 | 이벤트 스키마, 상태 추정, API, 로그 |
| 최적화·AI | 후보안 생성, 에이전트 평가, 설명 생성 |
| 안전·검증 | 제약 규칙, 시나리오 테스트, KPI 검증 |
| 디자인 | 세종·집현전 세계관을 현대 관제 UI에 절제해 적용 |

인원이 적으면 백엔드·최적화와 안전·검증을 통합한다.

## 3. 작업 순서

### 1단계: 뼈대

- 5개 교차로 데이터 스키마
- 정상·혼잡·사고 시나리오
- 정적 대시보드
- 기준 TOD와 KPI 계산

### 2단계: 추천

- 후보안 3개 생성
- 예상 KPI 계산
- 안전 규칙 구현
- AI 설명 구조화

### 3단계: 승인

- 승인·거절·보류
- 상태 전이와 감사 로그
- 적용 전후 비교
- 예측 오차 표시

### 4단계: 발표

- 3분 데모 자동 재생
- 장애 상황 대비 녹화본
- 발표 슬라이드와 수치 일치 검증
- 과장 표현 제거

## 4. 우선순위별 기능

### P0

- 재현 가능한 교통 시나리오
- 기준안·후보안 KPI 비교
- 안전 가드
- 운영자 승인
- 결정 로그

### P1

- 다중 에이전트 검토 시각화
- 장비 상태와 데이터 신뢰도
- 롤백 후보안
- 세종 지도 또는 한누리대로형 축 표현

### P2

- 실제 공개 데이터 연동
- 자연어 운영 질의
- 자동 리포트
- 긴급차량 우선 시나리오

## 5. 팀 규칙

- 기능 작업은 GitHub Issue와 연결한다.
- PR에는 데모 영향과 안전 영향이 있어야 한다.
- 시뮬레이션 수치는 실제 성과로 표현하지 않는다.
- 안전 규칙 변경은 최소 1명 추가 검토를 받는다.
- 발표 전날 이후에는 P0 버그 외 기능을 추가하지 않는다.
- 외부 API 장애가 나도 핵심 데모가 동작해야 한다.

## 6. 검증 체크리스트

- [ ] 안전 위반 후보안이 100% 차단되는가
- [ ] 승인 없이 적용 상태로 갈 수 없는가
- [ ] 데이터 지연 시 섀도 모드로 바뀌는가
- [ ] 같은 시드에서 같은 결과가 나오는가
- [ ] KPI 계산 정의가 문서와 코드에서 같은가
- [ ] 시뮬레이션 표기가 모든 결과 화면에 있는가
- [ ] 네트워크 없이도 핵심 데모가 가능한가
- [ ] 발표 수치가 저장된 실행 로그로 재현되는가
