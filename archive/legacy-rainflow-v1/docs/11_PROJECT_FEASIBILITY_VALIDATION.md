# Make Sejong Great Again 실현 가능성 검증 보고서

- 검증일: 2026-07-28
- 검증 대상: ZIP에 포함된 `00`~`08` 문서 9개
- 제외 대상: 별도 아이디어인 RainFlow Sejong 관련 문서
- 검증 범위: 문제 정의, 공개 근거, 제품 범위, MVP, 기술 구조, 일정, 발표 서사, 백로그

## 1. 최종 판정

이 프로젝트는 **합성 데이터 기반 5개 교차로 교통제어 오케스트레이터 데모**로 구현 가능하다.

다만 현재 문서와 공개자료만으로 다음 내용을 주장할 수는 없다.

- 실제 세종 교통망을 동기화한 디지털 트윈
- 세종시 실시간 교통 데이터 접근
- 실제 신호제어기 연동 또는 현장 제어
- 현장 수준의 안전성 보장
- 평균 지체 18% 또는 13% 개선이라는 실제 성과

따라서 해커톤에서는 다음과 같이 범위를 구분해야 한다.

| 범위 | 판정 | 조건 |
|---|---|---|
| 합성 데이터 기반 5개 교차로 시뮬레이션 | 가능 | 교차로 간 연결과 정체 전파를 모델링해야 함 |
| 기준 TOD와 후보안 2~3개 비교 | 가능 | 동일한 수요와 난수 시드로 비교 |
| KPI 계산 | 가능 | 수식, 단위, 측정 구간을 고정 |
| 결정론적 안전 가드 | 가능 | 구현된 데모 규칙 범위로 한정 |
| 운영자 승인과 감사 로그 | 가능 | 서버 측 상태 전이와 승인자 기록 필요 |
| 3분 오프라인 데모 | 가능 | 외부 API에 의존하지 않는 폴백 필요 |
| 실제 세종 데이터 읽기 연동 | 조건부 | 데이터 접근권과 스키마 확인 필요 |
| 실제 신호제어기 쓰기 연동 | 현재 불가 | 기관 승인, 표준, 보안, 장비 호환성 검증 필요 |
| 실제 도로 안전성·효과 입증 | 현재 불가 | 현장 실증과 독립적인 평가 필요 |

현재 저장소에는 문서만 있고 실행 코드, 테스트, 실행 로그가 없으므로 본 보고서는 **구현 가능성 검증**이며 실제 동작 검증은 아니다.

## 2. 문제 정의 근거 검증

### 2.1 확인된 사실

세종에는 CCTV, VDS, DSRC, VMS, BIS 등 ITS 기반이 존재한다. VDS는 교통량, 속도, 점유율을 수집하는 것으로 소개돼 있다. 다만 이 자료만으로 현재 장비 수, 장비 건전성, 외부 API 및 실시간 원천 데이터 접근 가능성을 확인할 수는 없다.

- [세종시 교통정보시스템](https://bis.sejong.go.kr/web/information/information_system.view)

2020년 국토교통부 자료에는 세종 1생활권 스마트교차로 14개소와 스마트횡단보도 10개소 실증 계획이 나온다. 이는 당시 구축·실증의 근거이며, 2026년 현재 모든 시설이 상시 정상 운영되고 있다는 근거는 아니다.

- [국토교통부 정책브리핑](https://www.korea.kr/multi/visualNewsView.do?newsId=148877347)

2025년 12월 세종시의회에서는 의원 발언을 통해 346개 교차로 온라인 신호제어시스템의 사실상 미사용, 서버 노후화, 데이터 동기화 중단 및 경찰의 현장 수동조작 문제가 제기됐다. 이는 공식 회의록에 기록된 문제 제기이지만 집행부의 기술진단 결과와 동일한 강도의 근거로 취급해서는 안 된다.

- [2025년 12월 세종시의회 회의록](https://council.sejong.go.kr/cms/mntsViewer.do?mntsId=6667)

2026년 2월 세종시 교통국장은 1~4생활권에서 인수한 온라인 신호제어기 약 366개를 조사했고 236개가 불량으로 파악됐다고 답변했다.

- [2026년 2월 세종시의회 회의록](https://council.sejong.go.kr/cms/mntsMmbrSimpleViewer.do?mntsId=6693&var08=MBR000064)

2026년 7월 회의록에는 세종시가 한국도로교통공단과 매년 신호체계 최적화 사업 및 교통량 전후조사를 수행한다는 내용이 나온다. 따라서 세종에 “신호 운영 소프트웨어나 최적화 업무가 전혀 없다”고 단정할 수는 없다.

- [2026년 7월 세종시의회 회의록](https://council.sejong.go.kr/cms/mntsViewer.do?mntsId=6785)

### 2.2 정정이 필요한 표현

#### 346개와 366개를 합치지 않는다

2025년 의원 발언은 346개 교차로를, 2026년 집행부 답변은 366대 제어기를 언급한다. 범위, 시점 또는 집계 단위가 다를 수 있으므로 하나의 통계처럼 합치면 안 된다.

또한 `236 / 366 = 64.5%`이므로 이를 계산된 사실로 `약 70%`라고 표현해서는 안 된다. 공식 발언을 소개해야 한다면 “교통국장은 약 70%라고 표현했으나 단순 계산은 64.5%”라고 출처와 산술을 분리해야 한다.

#### “운영 소프트웨어가 없다”는 단정을 완화한다

연례 신호체계 최적화와 전후조사가 이미 존재한다. 프로젝트가 해결하려는 문제는 다음처럼 정의하는 편이 정확하다.

> 주기적 신호 최적화 업무는 존재하지만, 실시간 다교차로 상태 통합, 복수 후보 검토, 결정론적 안전검사, 사람 승인, 적용 전후 효과기록을 하나로 연결하는 상시 폐루프 운영은 공개자료에서 확인되지 않았다.

#### 현재 장비 사용 가능성을 전제하지 않는다

스마트교차로와 C-ITS 실증 이력은 확인되지만 현재 접근권한, 데이터 스키마, 통신 프로토콜, 가용 장비 수와 복구율은 확인되지 않았다. MVP는 실제 데이터 접근을 전제로 해서는 안 된다.

## 3. 제품과 AI 역할 검증

### 3.1 제품 구조는 타당하다

다음 운영 흐름은 해커톤 데모로 구현할 수 있으며 제품 차별점도 명확하다.

1. 5개 교차로 상태와 정체 전파를 한 화면에 표시
2. 기준 TOD와 복수 후보안 생성
3. 교통 흐름, 보행 안전, 긴급 대응, 장비 신뢰도 관점 검토
4. 결정론적 안전 가드 실행
5. 운영자가 근거와 예상 KPI를 확인하고 승인 또는 거절
6. 디지털트윈형 시뮬레이션에 적용
7. 적용 전후 KPI와 판단 근거 기록

### 3.2 AI 책임 범위를 제한해야 한다

다교차로 신호 최적화와 안전성 검사는 LLM이 없어도 구현할 수 있다. “AI가 신호를 결정한다”는 설명보다 다음과 같은 책임 분리가 적절하다.

| 기능 | 책임 구성요소 |
|---|---|
| 신호 후보 생성 | 최적화 또는 제한 탐색 코드 |
| KPI 예측·계산 | 교통 시뮬레이터 |
| 안전 판정 | 버전이 고정된 결정론적 규칙 엔진 |
| 상황 요약 | AI |
| 복수 관점 부작용 검토 | AI |
| 운영자 설명문 생성 | AI |
| 최종 승인 | 사람 |

AI 출력은 구조화된 형식으로 제한하고, AI가 생성한 수치나 안전 판단을 그대로 적용해서는 안 된다. API 장애 시에는 기준 TOD 유지와 사전에 저장된 설명 또는 템플릿을 사용해야 한다.

### 3.3 복수 AI 관점의 표현

동일한 모델에 네 개 프롬프트를 호출하거나 한 번의 호출로 네 관점을 생성하는 것은 구현 가능하다. 다만 이를 서로 독립된 네 개의 지능형 시스템처럼 과장해서는 안 된다.

MVP에서는 다음 네 관점으로 통일하는 것이 적절하다.

- 교통 흐름
- 보행 안전
- 긴급 대응
- 장비·데이터 신뢰도

문서 02의 정책·운영 관점은 운영자 체크리스트 또는 후속 기능으로 분리한다.

## 4. 시뮬레이터와 KPI 구현 조건

### 4.1 5개 교차로 정체 전파

각 교차로를 독립적인 랜덤 큐로 만들면 “정체 전파”를 시연할 수 없다. 최소한 다음 데이터가 필요하다.

- 교차로 연결 그래프
- 링크 길이와 저장 가능 차량 수
- 링크 주행시간
- 방향별 회전 비율
- 차로군별 포화교통류율
- 차량의 유효 길이
- 상류 방출량과 하류 도착량 연결
- 하류 포화 시 상류 진입을 막는 spillback 처리

SUMO는 다교차로 신호 프로그램과 외부 제어 인터페이스를 지원하므로 확장 경로로 사용할 수 있다.

- [SUMO Traffic Lights](https://eclipse.dev/sumo/docs/Simulation/Traffic_Lights.html)

다만 48시간 해커톤에서는 SUMO 네트워크 작성과 패키징이 일정 위험이 될 수 있으므로 자체 큐 기반 시뮬레이터를 P0로 두는 것이 현실적이다.

### 4.2 KPI 정의

각 KPI에는 수식, 단위, 집계 시간, 반올림 방식이 필요하다.

- 평균 지체: 자유주행시간 대비 추가 소요시간
- 대기행렬: 차량 수 또는 미터 중 하나로 통일
- 정지율: 정지 판정 속도와 차량별 중복 집계 규칙 명시
- 보행 대기: 보행 수요, 호출 시각, 보행 현시가 필요
- spillback 위험: 링크 저장용량 대비 점유율로 계산

실측·학습 데이터가 없는 상태에서 “정체 전파 확률”이라고 표현하기보다 **spillback 위험 점수 또는 등급**으로 표현하는 것이 적절하다.

### 4.3 예측과 결과를 분리한다

같은 시뮬레이터의 동일 실행값을 예측값과 결과값으로 동시에 사용하면 예측 오차 검증이 순환 논리가 된다.

- 예측: 예측 수요 trace 또는 여러 수요 시나리오 사용
- 평가: 별도의 고정된 실현 수요 trace 사용
- 비교: 동일한 평가 수요와 동일한 난수 시드로 기준안과 후보안 실행

화면의 `actual`은 실제 도로 실측치가 아니라 **적용 후 시뮬레이션 관측 KPI**로 표기해야 한다.

## 5. 안전 가드 검증

### 5.1 구현 가능한 범위

안전 가드는 코드로 구현 가능하지만, 다음과 같은 “데모 규칙 집합”의 위반을 검사하는 수준이다.

- 보행 최소시간
- 최소·최대 녹색시간
- 황색시간과 전적색시간
- 상충 이동류 동시 허용 금지
- 허용된 현시 전환 순서
- 주기 합계 일치
- 분할과 오프셋 변경폭 제한
- 데이터 신선도
- 장비 상태

교차로별 상충행렬, 횡단보도 길이, 현시 순서와 승인된 안전시간이 없다면 현장 안전성을 검증할 수 없다.

한국도로교통공단은 교통신호제어기와 관련 장비에 대해 표준 준수와 기능·호환성 검사를 운영하고 있다.

- [한국도로교통공단 교통신호제어기 검사제도](https://kics.koroad.or.kr/intro/system.do)

따라서 발표에서는 다음처럼 표현해야 한다.

> 안전 가드는 합성 모델에 인코딩된 제약 위반을 결정론적으로 차단한다. 이는 실제 도로에 대한 안전 인증이나 현장 안전성 보장을 의미하지 않는다.

`위험 후보 100% 차단`도 모든 가능한 위험을 차단한다는 뜻으로 사용하면 안 된다. 다음과 같이 테스트 범위를 밝혀야 한다.

> 정의된 위반 fixture와 property-based 테스트가 생성한 모든 위반 사례를 차단했다.

### 5.2 승인 직전 재검사

후보 생성 시 안전검사를 통과했더라도 운영자가 승인하는 동안 데이터가 오래되거나 후보가 변경될 수 있다. 승인 및 적용 직전에 다음을 다시 확인해야 한다.

- 후보안 해시
- 안전 규칙 버전
- 데이터 신선도
- 장비 상태
- 승인자 권한

## 6. 상태 전이 수정안

문서 04의 `HUMAN_APPROVED → SIMULATED` 흐름은 운영자가 예상 KPI를 보고 승인한다는 제품 정의와 충돌한다.

권장 상태 흐름은 다음과 같다.

```text
CREATED
  → PREDICTED
  → AI_REVIEWED
  → SAFETY_PASSED | SAFETY_REJECTED
  → HUMAN_APPROVED | HUMAN_REJECTED
  → TWIN_APPLIED
  → EVALUATED
```

예외 상태도 필요하다.

- `EXPIRED`
- `SIMULATION_FAILED`
- `DATA_STALE`
- `APPLY_FAILED`
- `ROLLED_BACK`

디지털 트윈 적용 상태와 섀도 모드를 혼용해서는 안 된다.

- 실행 대상: 합성 시뮬레이션 / 실제 데이터 섀도 / 현장
- 데이터 상태: 정상 / 지연 / 결측 / 장비 이상

두 항목을 별도의 축으로 관리한다.

## 7. 문서 간 충돌

발표와 구현 전에 다음 충돌을 해소해야 한다.

1. 핵심 AI 관점이 문서에 따라 4개 또는 5개다.
2. 문서 03은 긴급차량 대응 후보를 필수로 두지만 문서 05는 긴급차량 시나리오를 P2로 둔다.
3. 문서 03은 데이터 지연·결측 이벤트를 필수로 두지만 장비 신뢰도 UI는 P1이다.
4. 문서 04의 실패 표는 안전 가드 실패 시 모든 후보를 거절한다고 하지만 핵심 데모는 후보 A만 탈락하고 B는 통과한다.
5. 승인 전에 예상 KPI가 필요하지만 상태 전이는 승인 후에 시뮬레이션하도록 작성돼 있다.
6. `APPLIED_SHADOW`와 디지털 트윈 적용 상태가 혼용돼 있다.

권장 정리 방식은 다음과 같다.

- 네 개 AI 관점으로 통일
- 후보 C는 긴급차량 입력이 없다면 `보수적 복구안`으로 변경
- 데이터 신선도 경고와 승인 차단을 P0에 포함
- 안전검사는 후보별로 수행
- 예측 시뮬레이션과 승인 후 평가 시뮬레이션 분리

## 8. 18%와 13% 데모 장면 검증

위험 후보 A가 지체를 18% 줄이지만 보행 최소시간 위반으로 탈락하고, 안전 후보 B가 13%를 줄여 승인되는 장면은 기술적으로 구현할 수 있다.

다만 다음 조건이 필요하다.

- 값이 화면에 하드코딩되지 않을 것
- 저장된 시나리오와 고정 난수 시드로 계산할 것
- 기준안과 후보안에 동일한 수요를 사용할 것
- 규칙 버전과 시뮬레이터 버전을 기록할 것
- 여러 시드의 평균과 변동 범위를 별도로 확인할 것
- 화면 전체에 `데모용 시뮬레이션`임을 표시할 것

화성 15개 교차로 사례의 기업 발표에도 정확히 13% 통행시간 단축 수치가 등장한다. 따라서 프로젝트의 13%를 실제 계산 없이 사용하면 외부 사례를 차용한 것처럼 보일 위험이 있다.

- [SKT 화성 교통신호 최적화 사례](https://news.sktelecom.com/196956)

가장 좋은 방법은 시뮬레이터가 산출한 소수점 결과를 그대로 사용하는 것이다. 예시는 다음과 같다.

- 후보 A 예측: 평균 지체 `-17.8%`, 안전 규칙 위반으로 탈락
- 후보 B 예측: 평균 지체 `-12.6%`, 안전검사 통과
- 후보 B 적용 후 시뮬레이션 관측: 평균 지체 `-11.9%`

위 숫자 또한 형식 예시일 뿐이며 실제 구현 결과로 대체해야 한다.

## 9. 감사 로그 요구사항

“판단을 재현한다”고 주장하려면 최소한 다음 정보를 함께 저장해야 한다.

- 시나리오 ID와 입력 데이터 스냅샷
- `observed_at`, `ingested_at`
- 교차로 및 링크 구성 버전
- 기준 TOD와 후보 파라미터
- 후보 점수와 동점 처리 방식
- 규칙 엔진 버전과 위반 코드
- 시뮬레이터 버전
- 모델과 프롬프트 버전
- AI 구조화 출력
- 난수 시드
- 승인자 ID와 승인 시각
- 승인·거절 사유
- 적용 전후 KPI

AI의 내부 사고과정을 저장한다고 표현해서는 안 된다. 저장 대상은 입력, 구조화된 출력, 규칙 결과와 의사결정 기록이다.

## 12. 예상 구현 규모

권장 축소안의 P0 구현에는 약 `8~12인일`이 필요하다.

| 작업 | 예상 |
|---|---:|
| 데이터 계약, 시나리오, fixture | 1인일 |
| 시뮬레이터, KPI, 후보 생성 | 3인일 |
| 안전 가드, 상태 전이, 감사 로그 | 2인일 |
| 관제 UI, 재생, 승인 흐름 | 2~3인일 |
| 통합, 오프라인 패키징, 리허설 | 1~2인일 |

숙련된 4명이라면 약 3일이 현실적이다. 48시간 행사라면 다음 기능은 P0에서 제외하는 것이 안전하다.

- SUMO 실시간 실행
- 실제 지도
- 라이브 다중 LLM 호출
- 긴급차량 ETA 연동
- 실제 세종시 데이터 연동

권장 책임 분리는 다음과 같다.

- 시뮬레이션·데이터·KPI
- API·상태 전이·안전 가드
- UI·재생·오프라인 패키징
- 제품·통합·검증·발표

## 14. 발표용 권장 문구

### 문제 정의

> 세종은 ITS와 신호개선 업무가 이미 있지만, 2025~2026년 중앙 원격제어와 현장 제어기의 문제도 공식 석상에서 확인됐다. 우리는 그 원인을 해결했다고 주장하지 않고, 합성 5개 교차로 환경에서 데이터, 후보 생성, 제약검사, 사람 승인, 효과기록을 연결하는 운영 흐름을 검증한다.

### 제품 정의

> 본 프로젝트는 실제 신호기를 제어하는 시스템이 아니라 합성 교통환경에서 다교차로 운영 의사결정 과정을 검증하는 디지털트윈형 프로토타입이다.

### 안전성

> AI는 신호를 직접 결정하지 않는다. 후보는 최적화 코드가 생성하고, 안전 가드는 구현된 규칙 집합을 결정론적으로 검사하며, 운영자 승인 없이는 적용 상태로 넘어가지 않는다.

### 성과 수치

> 화면의 개선율은 실제 세종시 성과가 아니라 동일한 합성 수요와 고정 난수 시드에서 계산된 데모용 시뮬레이션 결과다.

## 15. 출처 관리 원칙

각 주장에는 다음 분류 중 하나를 표시하는 것이 적절하다.

- 공식 집행부 답변
- 정부 사업 소개
- 의원 문제 제기
- 기업 보도자료
- 연구 또는 특허
- 팀의 추론
- 검증이 필요한 가설
- 목표
- 시뮬레이션 결과

출처 문서는 단순 링크 목록보다 다음 필드를 가진 `claim-evidence matrix`로 관리하는 것이 좋다.

| 필드 | 내용 |
|---|---|
| Claim ID | 발표 문장 식별자 |
| Claim | 정확한 주장 |
| Type | 사실, 발언, 추론, 가설, 목표, 시뮬레이션 |
| Date | 근거 기준일 |
| Scope | 대상 지역과 장비 범위 |
| Source | 1차 출처 |
| Confidence | 확인, 부분 확인, 미확인 |
| Note | 제한사항과 최신성 |
